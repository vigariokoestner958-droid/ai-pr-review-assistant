## 二、误报归因分析

基线评测发现 **31个误报**，按根本原因分为以下4类：

---

### 类型 A：严重度过激（20个，占误报64%）

**根本原因：** System Prompt 中对 HIGH/MEDIUM/LOW 的定义模糊，AI 默认将一切发现的问题都标记为 HIGH 以示"认真"。

**典型案例：**

| 用例 | AI实际输出 | 正确级别 | 误报原因 |
|------|-----------|---------|---------|
| `QUAL-E-001` 裸except | HIGH | LOW | 裸except是代码风格问题，不可直接被攻击者利用 |
| `QUAL-E-002` 资源未关闭 | HIGH | LOW | 影响稳定性但非安全漏洞，且需长期积累才出问题 |
| `QUAL-E-003` 可变默认参数 | HIGH | LOW | Python经典陷阱，但不涉及安全或数据丢失 |
| `QUAL-E-005` 魔法数字 | HIGH | LOW | 纯代码可读性问题 |
| `QUAL-E-006` 没有输入验证 | HIGH | MEDIUM | 缺少格式校验不等于安全漏洞，取决于是否为系统边界 |
| `QUAL-E-008` 硬删除无软删除 | HIGH | LOW | 业务设计选择，非安全缺陷 |
| `PERF-E-005` 循环内字符串拼接 | HIGH | MEDIUM | 性能问题，非安全威胁 |
| `PERF-E-007` 数据库连接未复用 | HIGH | MEDIUM | 资源效率问题，极端情况才影响稳定性 |
| `PERF-E-008` 无索引高频查询 | HIGH | MEDIUM | 性能退化，非立即崩溃 |
| `PERF-H-001` 分布式锁粒度粗 | HIGH | MEDIUM | 性能瓶颈，非数据安全问题 |

**修复方案：** 在 System Prompt 中明确定义三级标准：
```
HIGH   = 可被外部攻击者直接利用 OR 导致数据丢失/服务崩溃
MEDIUM = 存在真实风险但需要特定条件，或影响范围有限
LOW    = 代码质量/可维护性，无直接安全或稳定性影响
```

**修复效果：** 代码质量类准确率 27% → 75%（+48pp）

---

### 类型 B：上下文理解不足（7个，占误报23%）

**根本原因：** AI 看到安全敏感关键词（如 `jwt`, `redis`, `random`）就条件反射报警，未真正理解上下文中的用法是否安全。

**典型案例：**

| 用例 | AI误报内容 | 实际情况 | 误报原因 |
|------|-----------|---------|---------|
| `CLEAN-001` 规范的参数化查询 | "SQL注入风险" | 使用了问号占位符，完全正确 | 看到SQL关键词就报 |
| `CLEAN-006` 规范的JWT | "JWT密钥风险" | 从环境变量读取，有过期时间，完全正确 | 看到jwt.encode就警觉 |
| `CLEAN-004` 规范异步HTTP | "并发风险" | 正确使用aiohttp，有超时设置 | 看到requests/aiohttp就报 |
| `EDGE-003` 安全的数学eval | "代码执行漏洞" | 用AST实现，不执行任意代码 | 看到eval就触发 |
| `CLEAN-009` 规范配置管理 | "敏感信息暴露" | pydantic从.env加载，无硬编码 | 看到database_url就报 |

**修复方案：** 在 System Prompt 添加负面引导：
```
- 看到好的代码实践（参数化查询、bcrypt哈希、有过期的JWT）→ 不要误报
- 如果一段代码没有直接暴露给外部攻击者，不能评为 HIGH
```

**修复效果：** 干净代码类准确率 67% → 93%（+26pp）

---

### 类型 C：JSON解析错误（4个，实际造成ERROR而非误报）

**根本原因：** 当代码片段包含中文注释、单引号嵌套或特殊字符时，AI 输出的 JSON 中会出现未转义的字符，导致解析失败。

**发生用例：**

| 用例 | 错误信息 | 代码特征 |
|------|---------|---------|
| `SEC-M-001` SSRF | `Expecting ',' delimiter: line 11 col 29` | 含中文注释 |
| `SEC-H-003` 二次SQL注入 | `Expecting ',' delimiter: line 11 col 25` | 含中文注释+单引号 |
| `PERF-H-002` 热key问题 | `Expecting ',' delimiter: line 13 col 347` | 含中文注释+Redis命令 |
| `QUAL-H-003` 类型混淆 | `Expecting ',' delimiter: line 10 col 92` | 含中文注释 |

**修复方案：** Layer 1/2 均新增重试逻辑，第一次 JSON 解析失败时自动重试并附加修正提示：
```python
for attempt in range(2):
    raw = self._call(...)
    try:
        d = json.loads(_strip_code_fence(raw))
        break
    except json.JSONDecodeError:
        if attempt == 1: raise
        context += "\n\n[请重新输出合法JSON，不要包含注释或特殊字符]"
```

**修复效果：** 基线4个ERROR → 修复后0个ERROR

---

### 类型 D：边界判断分歧（4个，占误报13%）

**根本原因：** 部分用例的正确答案本身有歧义，AI 的判断与我们的预期不同，但都有合理依据。

**典型案例：**

| 用例 | 我们的预期 | AI的判断 | 分析 |
|------|-----------|---------|------|
| `SEC-H-009` 日志注入 | 无HIGH（LOW即可）| HIGH | 日志注入确实可以伪造审计记录，AI判断有一定依据 |
| `SEC-H-010` 依赖混淆 | 无HIGH | HIGH | 供应链攻击确实严重，AI的严格判断有道理 |
| `EDGE-009` 混合代码（好代码+1个隐藏问题）| 无HIGH | HIGH | AI正确发现了SECRET默认值问题，我们的预期设置过松 |
| `EDGE-012` 依赖注入正确实现 | 无HIGH | HIGH | AI可能对OAuth配置过于警觉 |

**这类误报的特点：** 不是AI的错误，是测试用例的预期设置过于严格或有歧义。实际上这类"误报"在真实使用场景中可能是有价值的提示。

## 三、漏报归因分析

基线评测发现 **3个漏报**（预期 HIGH 但 AI 未识别）：

---

### 漏报 1：`SEC-E-007` CORS配置通配符

**代码：**
```python
app.add_middleware(CORSMiddleware, allow_origins=["*"], allow_credentials=True)
```

**漏报原因：**
- 代码片段极短，缺少上下文
- AI 可能将 `allow_origins=["*"]` 判断为仅是配置问题（MEDIUM），未意识到与 `allow_credentials=True` 的组合才是 HIGH
- FastAPI 专项知识：这个组合在浏览器端会被阻止，AI 可能了解到这一点所以降低了严重度

**改进方向：** 在 Prompt 中明确列举"CORS allow_origins=* + allow_credentials=True 的组合 = HIGH"

---

### 漏报 2：`SEC-H-003` 二次SQL注入

**代码：**
```python
# 存储时参数化（安全）
db.execute("UPDATE users SET username=? WHERE id=?", (new_username, user_id))
# 读出后直接拼接（危险）
posts = db.execute(f"SELECT * FROM posts WHERE author='{username}'")
```

**漏报原因：**
- 这是 "second-order injection"（二次注入），需要跨函数理解
- 两个函数出现在同一文件，但逻辑上是先存后读，AI 需要理解执行时序
- 第一次评测中此用例触发了 JSON 解析错误（中文注释），导致漏报
- 修复解析错误后，AI 实际上可以正确识别此问题

**改进方向：** 加重试后此问题基本解决；可在 Prompt 中增加"注意跨函数的数据流"引导

---

### 漏报 3：`PERF-E-002` 全表扫描后内存过滤

**代码：**
```python
all_posts = db.execute("SELECT * FROM posts ORDER BY created_at DESC").fetchall()
user_posts = [p for p in all_posts if p['author_id'] in get_following(user_id)]
```

**漏报原因：**
- 修复后 Prompt 将此类问题定义为 MEDIUM 而非 HIGH
- 原本我们预期为 HIGH，但这是**测试用例设计的问题**：全表扫描是严重性能问题，但不会直接导致数据丢失或安全漏洞，评为 MEDIUM 也是合理的
- 这实际上是"漏报测试标准过严"，而非 AI 真的漏报

**结论：** 修复 Prompt 后，此类问题的准确分级其实是 MEDIUM，测试预期应调整
